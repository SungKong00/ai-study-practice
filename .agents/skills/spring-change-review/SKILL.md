# Spring 변경 리뷰

요청받은 커밋·PR·작업 트리를 검토한다. 브랜치는 공통 조상부터 비교한다. 커밋 전에는 `git diff HEAD`를 보고 `git status --short`에만 나오는 새 파일도 직접 읽는다. 리뷰만 요청받으면 결과를 의견으로 전달한다.

변경 경로와 승인 예시로 `openspec/specs/product-*/spec.md`의 요구사항·시나리오를 찾는다. 검색과 정렬처럼 같은 예시에서 결합되는 계약은 각 원본을 함께 대조한다. 계약 변경은 [진행 중인 변경](../../../openspec/changes/)의 시나리오, 저장 방식 변경은 [관련 ADR](../../../docs/adr/)을 함께 본다.

- **요청·응답** — 실제 JSON이 Jackson·Bean Validation 중 어디까지 도달하는지 본다. 거절할 입력은 HTTP 상태와 기존 데이터 보존을 확인한다. 공통 설정은 다른 DTO에 미치는 영향도 본다.
- **설계·확장** — 대표 호출자에서 규칙·상태의 소유자까지 따라간다. 새 호출자가 검증·호출 순서·실패 복구를 복제하거나 규칙을 우회할 수 있으면 그 경로와 가장 작은 수정안을 제시한다. 패턴을 제안할 때는 독립적으로 바뀌는 부분과 함께 유지해야 할 규칙을 짚는다.
- **컨벤션** — 같은 모듈의 유사 진입점, 테스트 또는 ADR과 대조한다. 차이가 호출자의 기대나 다음 변경에 미치는 영향을 설명할 수 있을 때 지적한다.
- **서비스·JPA** — 호출이 트랜잭션 프록시를 거치는지, 함께 성공해야 할 쓰기가 어디서 커밋되는지 본다. 목록은 쿼리부터 응답까지 약속한 항목과 순서가 유지되는지 확인한다.
- **저장 설정** — JDBC URL과 스키마 생성 설정을 함께 본다. 테스트 초기화가 데이터 수명 차이를 가리면 같은 작업 디렉터리에서 앱을 종료·재시작한 뒤 상품 목록을 다시 조회한다.

전후를 구별할 입력을 고르고 기존 테스트가 그 조건을 거치는지 확인한다. 필요하면 [Gradle Wrapper](../../../README.md)로 해당 테스트를 실행한다.

지적은 영향이 큰 순서로 **변경 파일·줄, 재현 조건, 기대값과 달라지는 결과**를 적는다. 실행했다면 테스트나 요청을, 추론했다면 코드 근거를 밝힌다. 미결 정책은 `확인 필요`로 표시하고 선택에 따라 달라질 동작을 묻는다. 사용자 선택이 [프로젝트 ADR 기준](../../../AGENTS.md)에 해당하면 기존 결정을 조회한다. 리뷰에서는 기록할 결정·대안·영향을 제안하고, 구현 시 확정된 선택과 이유를 기록한다. 지적이 없는 로컬 리뷰도 확인한 설계 경로나 회귀 조건 하나와 그 근거를 짧게 남긴다.
