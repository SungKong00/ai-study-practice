# 팀 요청의 근거를 Git 커밋에 고정한다

## Context and Problem Statement

상품명 검색은 구현과 기준 명세가 서로 다른 PR로 main에 들어갔다. Discord는 로컬 Git을, n8n 폼은 GitHub의 파일을 읽는다. 같은 질문을 한 시점으로 재현하고 승인 대기 중 바뀐 근거를 식별할 공통 단위가 필요하다.

## Considered Options

- 채널마다 현재 파일을 바로 읽는다. 배치는 단순하지만 파일을 여러 번 읽는 사이 기준 브랜치가 바뀔 수 있고, 단일 파일 해시로는 당시의 구현을 알 수 없다.
- 명세·코드 요약을 별도 위키나 검색 DB의 원본으로 삼는다. 검색은 빨라지지만 정책 수정과 색인 확정의 순서, 과거 근거의 보존을 별도로 운영해야 한다.
- 요청마다 저장소 커밋을 고정하고 그 시점의 현재 명세와 코드에서 필요한 부분을 찾는다. 파일을 분리해도 이전 근거는 커밋으로 복원할 수 있다.

## Decision Outcome

세 번째 방식을 제안한다. 제품 담당자가 합의한 현재 계약은 기준 명세, 구현된 동작은 같은 커밋의 실행 코드로 확인한다. 승인한 이슈에는 저장소·커밋과 인용 위치를 보존한다. 목차와 캐시는 Git에서 다시 만들 수 있다. 이 원칙은 Discord·접수 폼의 현재 상태 판정과 로컬 리뷰의 변경 전후 비교에 적용한다.

### Consequences

Good, because 검색 도입 전후에 같은 질문을 재생하고, 명세에만 있거나 코드에만 있는 기능을 식별할 수 있다.

Bad, because 원격 기준을 읽을 수 없을 때 현재 지원 판정이 지연된다. 담당자는 마지막으로 확인한 커밋을 보고 재시도할 수 있다.

GitHub 브랜치와 승인 DB는 서로 다른 시스템이다. 승인 직전에 확인한 커밋을 기록하고 구현 PR에서도 최신 기준을 다시 대조한다. 실제 배포 여부를 묻는 요청에는 별도로 배포된 커밋이 필요하다.
