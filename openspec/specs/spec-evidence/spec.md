# spec-evidence Specification

## Purpose

기획자와 개발자가 같은 시점의 상품 명세와 실행 코드를 찾아 지원 여부를 판단하고, 규칙이 바뀌거나 파일이 나뉜 뒤에도 그 판단을 검증할 수 있게 한다.

## Requirements

### Requirement: 현재 제품 동작의 판정

팀 요청 접수는 설정된 제품 기준 브랜치에서 원격으로 확인한 한 커밋의 현재 명세와 구현으로 지원 여부를 판정해야 한다(MUST). 근거에는 해당 커밋, 파일 경로, 요구사항 제목 또는 코드 위치, 원문 인용을 표시한다.

#### Scenario: 여러 규칙을 조합하는 문의
- **WHEN** 상품명 완전 일치 검색과 가격 정렬을 함께 지원하는 시점에 두 기능을 조합할 수 있는지 묻는다.
- **THEN** 검색·정렬 양쪽 근거와 이를 함께 적용하는 구현을 제시하고 이슈를 생성하지 않는다.

#### Scenario: 현재 명세와 코드의 차이
- **WHEN** 실행 코드에 이름 필터가 있지만 기준 명세에 해당 계약이 없고 보관된 변경 문서에만 설명이 있다.
- **THEN** 구현에서 확인한 동작과 명세에 빠진 항목을 구분해 담당자 확인을 안내한다. 과거 문서를 현재 계약으로 인용하지 않는다.

#### Scenario: 근거를 확인할 수 없는 문의
- **WHEN** 기준 브랜치의 최신 커밋 조회가 실패하거나 허용 범위 안에서 질문을 판별할 증거가 부족하다.
- **THEN** 확인이 필요한 이유와 마지막 확인 시점이 있으면 그 시점을 표시하고 현재 지원·미지원 확정과 이슈 발행을 보류한다.

### Requirement: 명세 이동 전후의 탐색

팀은 요구사항을 독립된 기능 명세로 옮겨도 동작을 바꾸지 않은 항목과 시나리오를 모두 찾을 수 있어야 한다(SHALL). 커밋 기반으로 승인·게시한 근거는 당시 커밋의 원문을 가리켜야 한다(MUST). 이전 방식의 게시본은 저장된 파일 해시·본문·번호를 보존하고 확인 불가능한 커밋은 미기록으로 표시한다.

#### Scenario: 검색만 분리한 뒤 두 파일이 필요한 문의
- **WHEN** 상품명 검색 요구사항과 그 시나리오만 새 파일로 옮긴 뒤 “노트를 싼 순으로 보면 노트북도 나와요? 가격이 같으면요?”라고 묻는다.
- **THEN** 같은 커밋에서 새 파일의 이름 일치 규칙과 기존 목록 파일의 정렬·동률 규칙, 두 조건을 함께 적용하는 구현을 찾아 인용한다. 응답은 이동 전과 같고 과거 이슈의 인용은 당시 경로에서 열린다.

#### Scenario: 조합한 질문에서 한 조건의 근거가 비는 경우
- **WHEN** 현재 검색 규칙은 확인했지만 목록의 정렬 원본을 읽을 수 없거나 그 원본과 실행 코드가 충돌한다.
- **THEN** 확인된 이름 일치 조건을 안내하고 정렬·동률은 확인이 필요하다고 표시한다.

### Requirement: 승인 예시로 명세 위치 결정

승인된 이슈의 담당 개발자는 OpenSpec 제안에서 기존 명세와 완료 예시를 대조해 대상 기능과 선택 이유를 명시하고, 동료 리뷰어는 기능 PR에서 예시 보존과 중복 정의를 확인해야 한다(MUST).

#### Scenario: 같은 상품 동작의 변경
- **WHEN** 기획자가 “노트로 노트북도 찾기”의 기대 결과를 승인하고 기존 상품명 검색 규칙이 그 동작을 정의한다.
- **THEN** 개발자는 제안에서 기존 검색 항목을 수정 대상으로 고른다. 리뷰어는 새 검색 예시와 함께 기존 입력 오류·정렬 예시가 보존됐는지 확인한다.

#### Scenario: 독립적으로 검토할 검색 정책
- **WHEN** 동의어·품절 노출 추가로 검색 대상을 정하는 예시를 목록 순서와 따로 검토할 필요가 생긴다.
- **THEN** 개발자는 새 검색 명세가 맡을 질문과 기존 목록에 남길 규칙을 제안한다. 리뷰어는 결합 예시가 두 규칙으로 이어지고 정렬 규칙의 원본이 한 곳인지 확인한다.

### Requirement: 제품 변경의 인계와 검토

승인된 제품 계약 변경은 이슈의 완료 예시, 해당 OpenSpec 변경 항목, 실제 검증 결과를 연결하고 구현과 기준 명세를 같은 기능 PR에서 검토해야 한다(MUST).

#### Scenario: 기능 PR을 준비할 때
- **WHEN** 개발자가 승인된 상품 요청을 구현한 뒤 PR 제출을 요청한다.
- **THEN** 로컬 Spring 리뷰가 기존 계약·승인 예시·설계·컨벤션을 확인한 뒤 공통 PR 양식에 근거와 검증 결과를 채운다. 코드와 기준 명세가 머지되면 다음 문의는 새 계약으로 판정한다.

#### Scenario: 중간 검증 요청 없이 구현을 끝낸 경우
- **WHEN** 개발자가 별도 검증 단계를 요청하지 않고 PR 제출을 요청한다.
- **THEN** PR 준비는 승인 예시와 구현·테스트를 대조하고 결과를 기록해야 한다(MUST). 회귀가 발견되면 제출 전에 수정하고 재검증한다.

#### Scenario: 변경 전체 또는 일부를 PR로 제출
- **WHEN** 검증된 변경을 제출할 때 남은 미구현 작업이 있는지 확인한다.
- **THEN** 전체가 완료된 변경은 기준 명세 반영을 확인한 뒤 보관하고, 부분 PR은 검증된 범위만 동기화한 채 변경안을 열어 둔다.

#### Scenario: 구현 중에 승인 범위가 달라질 때
- **WHEN** 개발 중 선택한 방식 때문에 승인된 예시의 사용자 결과가 달라진다.
- **THEN** 변경된 예시를 기획 담당자가 확인한 뒤 이슈와 변경안에 반영한다. 같은 결과를 유지하는 JPA 쿼리 선택은 개발자가 결정한다.
