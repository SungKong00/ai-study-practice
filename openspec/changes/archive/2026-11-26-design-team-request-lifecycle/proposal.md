## Why

상품명 검색을 구현한 PR #6과 기준 명세를 반영한 PR #7 사이에는 코드와 명세의 답이 달랐다. 팀원이 Discord에서 승인한 제품 결정을 개발자가 그대로 이어받고, 머지한 뒤에는 다음 요청자가 바뀐 동작을 확인할 수 있어야 한다.

## What Changes

- n8n이 별도 Python 서비스 없이 Discord 이벤트와 접수 폼을 받아 한 시점의 상품 명세·구현을 근거로 답한다. 문의, 근거 부족, 제품 결정이 필요한 요청을 구분한다.
- Discord에서 공식 OpenSpec 탐색 스킬로 대화하고, 변경 의사가 확인되면 전용 이슈 구체화 스킬로 이유·범위·완료 예시를 합의한다. Discord 산출물은 공통 이슈 양식으로 작성한 초안이다. n8n은 승인된 판본만 GitHub 이슈로 게시하고, 승인 직전 바뀐 근거와 불명확한 게시 결과를 처리한다.
- 개발자는 승인 예시로 OpenSpec 제안을 작성하면서 수정할 기존 요구사항 또는 분리할 규칙을 고른다. 구현 중 검증은 개발자가 선택한다. PR 준비 시 승인 예시 검증, 기준 명세 반영, 완료 변경 보관, Spring 리뷰를 수행하고 사람이 CI와 최종 diff를 확인한다.
- 과거 커밋, 문서 이동, 동시 승인과 응답 유실을 재현해 하네스·모델 변경의 품질과 비용을 비교한다.

## Capabilities

### New Capabilities

- `spec-evidence` — 팀이 현재 제품 동작의 근거를 찾고, 정책을 변경·분리한 뒤에도 같은 질문을 검증하는 방식.
- `team-request-intake` — 문의를 처리하고 제품 요구를 구체화해 사람이 승인한 이슈로 인계하는 과정.

## Impact
