## Purpose

팀원의 상품 문의를 확인 가능한 답변 또는 구체적인 기능 요청으로 정리하고, 사람이 확인한 판본만 한 건의 GitHub 이슈로 인계하며 실패 후에도 그 결과를 대조할 수 있게 한다.

## ADDED Requirements

### Requirement: 문의와 변경 의사의 구분

단순 문의는 확인한 사실로 답하고, 변경 의사가 있으며 사용자 결과가 달라지는 선택이 남으면 예시로 질문해야 한다(MUST). 제품 조건이 정해지면 로컬과 Discord가 공유하는 양식에 불편·원하는 동작·완료 예시를 채워야 한다(SHALL).

#### Scenario: 기능이 없는 시점의 단순 문의
- **WHEN** 이름 필터 도입 전 구현과 명세를 확인할 수 있고 “이름으로 찾을 수 있어요?”라는 문의만 들어온다.
- **THEN** 폼과 Discord는 확인한 현재 조회 범위와 미지원 근거를 답한다. 요청자가 변경을 원한다고 밝히기 전에는 게시할 초안을 만들지 않는다.

#### Scenario: 답을 들은 뒤 같은 글에서 추가를 요청
- **WHEN** 미지원 안내를 받은 기획자가 같은 Discord 글에 “그럼 이름 검색을 추가해 주세요”라고 답한다.
- **THEN** 봇은 그 글에서 원하는 검색 결과를 묻고 같은 요청 ID로 승인용 판본을 준비한다.

#### Scenario: n8n 단독 수신
- **WHEN** 별도 봇 프로세스 없이 지정 포럼에서 사람이 새 글이나 답글을 쓰고 담당자가 그 글의 버튼을 누른다.
- **THEN** n8n은 같은 글에서 응답하고 유효한 담당자·최신 판본만 게시한다. 다른 포럼의 글, 봇 메시지, 같은 이벤트의 재전달은 새 요청을 만들지 않는다.

#### Scenario: 앞부분 일치와 포함 검색의 차이
- **WHEN** 요청자가 “노트를 찾으면 노트북도 나오게 해주세요”라고 한다.
- **THEN** “스프링 노트도 포함하나요?”처럼 결과를 가르는 질문을 한다. 합의한 예시는 이슈 초안에 남기고 저장소 메서드 선택은 개발자에게 맡긴다.

#### Scenario: 명령어 없이 대화에서 변경 요청으로 전환
- **WHEN** 기획자가 기존 검색 결과에 관해 일반 대화를 이어가다가 부분 검색을 요청한다.
- **THEN** 봇은 같은 스레드에서 탐색을 이어가고 변경 의사가 확인된 턴부터 이유·변경 범위·완료 예시를 구체화해야 한다(MUST). 이미 확인한 조건은 재사용하고 사용자 결과가 갈리는 질문이 남으면 승인 가능한 초안을 내지 않는다.

#### Scenario: 기획에서 개발로 넘기는 산출물
- **WHEN** 기획자가 기존 검색을 포함 검색으로 바꾼다고 결정하고 포함·제외 예시를 확인한다.
- **THEN** 봇은 제품 결정을 공통 이슈 양식으로 제시하고 담당자의 판본 승인을 기다린다. Discord 대화에서 OpenSpec 변경 폴더를 생성하지 않는다.

### Requirement: 승인한 판본의 게시

Discord에서 담당자가 초안을 고쳐 전문을 다시 볼 수 있어야 한다(SHALL). 유효한 권한과 최신 판본을 확인한 승인만 이슈를 게시하며, 표시한 제목·본문과 게시한 제목·본문이 일치해야 한다(MUST).

#### Scenario: 수정과 동시 승인
- **WHEN** 1판을 보던 중 수정이 먼저 저장되고 Discord와 폼에서 구판·신판 승인 요청이 겹친다.
- **THEN** 구판 승인은 새 초안을 보여준다. 신판을 유효하게 승인한 요청만 게시 권한을 얻고, 재클릭은 같은 등록 상태 또는 이슈 번호를 돌려준다.

#### Scenario: 게시 권한이 없는 팀원
- **WHEN** 일반 참여자가 제품 조건을 제안하거나 승인 동작을 시도한다.
- **THEN** 대화에 의견을 남길 수 있다. 게시용 판본의 수정·승인은 권한 있는 담당자가 수행한다.

#### Scenario: 수정으로 기존 기능과 같아진 요청
- **WHEN** 담당자가 부분 일치 초안의 완료 예시를 이미 지원 중인 완전 일치로 바꾼다.
- **THEN** 현재 커밋이 같더라도 수정된 동작을 다시 판정해 지원 근거를 안내하고 옛 승인 토큰을 만료한다. 이슈는 생성하지 않는다.

### Requirement: 승인 직전의 근거 재확인

게시 직전에는 최신 제품 근거를 다시 확인해야 한다(MUST). 무관한 변경은 기존 승인을 살리고, 관련 판단이나 표시할 내용이 달라진 경우 갱신한 결과를 사람에게 제시해야 한다(MUST).

#### Scenario: 승인 대기 중 정책 변경
- **WHEN** 승인 대기 중 요청한 기능이 이미 머지돼 기준 명세와 구현 모두에서 지원한다.
- **THEN** 변경된 근거와 사용법을 보여주고 대기 초안을 종료한다. 옛 버튼과 검토 폼 모두 이 요청으로 이슈를 만들 수 없다.

#### Scenario: 같은 동작에 무관한 커밋
- **WHEN** 하네스 설명만 바뀌고 승인된 제품 근거·제목·본문은 그대로다.
- **THEN** 최근 확인한 커밋을 기록하고 보여준 판본 그대로 게시한다. 최신 근거 조회에 실패한 경우에는 초안을 보존하고 재확인을 안내한다.

### Requirement: 모호한 등록 결과의 복구

GitHub의 생성 여부를 확정할 수 없으면 재생성 전에 승인 판본과 기존 이슈를 대조해야 한다(MUST). 이전 버전으로 만든 요청의 게시 결과와 복구 근거를 보존해야 한다(SHALL).

#### Scenario: GitHub에 생성된 뒤 응답 유실
- **WHEN** 이슈 생성 응답을 잃어버린 뒤 담당자가 같은 요청을 다시 승인한다.
- **THEN** 생성 확인 중 상태를 돌려준다. 대상 저장소의 요청 표식·제목·본문이 일치하는 이슈 번호를 연결하면 기존 한 건으로 종결한다.

#### Scenario: 이전 버전의 승인 대기 건
- **WHEN** 단일 명세 파일 해시만 저장한 기존 초안에 새 처리 방식으로 승인 요청이 들어온다.
- **THEN** 최신 근거로 전문을 다시 구성하여 담당자에게 보여주고 새 판본 승인을 받는다. 이미 게시된 건은 기존 이슈 번호를 그대로 반환한다.
